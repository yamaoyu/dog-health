# Issue 作成

このSkillは、ユーザーの要求をこのリポジトリ向けの焦点が定まった GitHub Issue に変換するために使う。

## 手順

1. ユーザーの要求を理解し、意図された変更を具体的な言葉で整理する。
2. 実装方針を決める前にリポジトリを調査する。`AGENTS.md`、`README.md`、`docs/`、`.github/ISSUE_TEMPLATE/`、関連するフロントエンド/バックエンドコード、テスト、API定義、データベース定義を確認する。
3. 現在の動作、期待する動作、関連ファイル、アーキテクチャ上の制約、ユーザー要求とリポジトリ現状の矛盾を整理する。
4. 要求の種類に応じてIssueテンプレートを選ぶ。
5. 有用な最小スコープを定義する。1つのIssueは、焦点の定まった1つのPRに収まる大きさにする。
6. 要求が大きすぎる場合は、Issueを作成する前に止まり、分割案を提示する。
7. 対象外を明確にする。特に、ユーザーが明示していない認証、分析、通知、admin機能は対象外にする。
8. 実装後に客観的に確認できる受け入れ条件を書く。
9. 必要な検証を整理する。テスト、型チェック、ビルド、lintが存在する場合のlint、手動確認を含める。
10. 実装上の補足は、リポジトリ調査で確認できた内容だけを書く。
11. 最終的なテンプレート種別、タイトル、本文を簡潔に提示し、Issue作成前にユーザーへ確認する。
12. GitHub MCP/GitHubコネクタを使ってIssueを作成する。コネクタまたは必要なIssue作成ツールが利用できない場合はユーザーに伝え、`gh` や生のAPI呼び出しなどの代替手段を勝手に使わない。

## リポジトリルール

- `AGENTS.md` に従う。
- フロントエンドとバックエンドの関心を分離する。
- 汎用化された設計より、シンプルで保守しやすいMVPスコープを優先する。
- 明示的に依頼されない限り、大きな依存関係、認証、分析、通知、管理者機能を追加しない。
- バックエンド作業では、ルーターを薄く保ち、入力を Pydantic で検証し、複数形のリソースエンドポイントを使う。
- フロントエンド作業では、Vue 3、TypeScript、Composition API、機能単位のディレクトリ、Vitestによるテストを使う。

## Issue本文形式

`.github/ISSUE_TEMPLATE/` にあるテンプレートから、要求に最も合うものを選ぶ。

- 機能追加: `feature_request.md` を使う。新しいユーザー向け機能、既存機能の拡張、画面/API/データ操作の追加に使う。
- バグ修正: `bug_report.md` を使う。現在の動作が期待と異なる、エラーが出る、再現できる不具合がある場合に使う。
- タスク: `task.md` を使う。リファクタ、環境整備、テスト追加、CI改善、ドキュメント整備、依存関係の整理など、ユーザー向け機能追加や不具合修正ではない開発作業に使う。

どれにも明確に当てはまらない場合は、ユーザーに不要な質問をせず、調査結果から最も近いテンプレートを選び、選定理由をIssue作成前の確認に含める。

### 機能追加

`feature_request.md` の構造に沿って書く。

```markdown
### 概要

何を、なぜ変更するのか。

### 背景・現状

現在の動作、関連コード、背景。

### 対象範囲

今回実装する範囲。

### 対象外

今回実装しないもの。

### 受け入れ条件

- [ ] 客観的に確認可能な条件

### 検証方法

- 実行するテスト、型チェック、ビルド、手動確認

### 実装上の補足

調査で判明した関連ファイル、コンポーネント、API、注意事項。
```

### バグ修正

`bug_report.md` の構造に沿って書く。再現手順がリポジトリ調査だけで確定できない場合は、分かっている範囲と不足情報を明示する。

```markdown
### 概要

何が壊れていて、なぜ修正するのか。

### 現在の動作

実際に起きている問題。

### 期待する動作

本来あるべき動作。

### 再現手順

1. 

### 影響範囲

影響を受ける画面、API、データ、ユーザー操作。

### 対象範囲

今回修正する範囲。

### 対象外

今回修正しないもの。

### 受け入れ条件

- [ ] 客観的に確認可能な条件

### 検証方法

- 実行するテスト、型チェック、ビルド、手動確認

### 実装上の補足

調査で判明した関連ファイル、コンポーネント、API、注意事項。
```

### タスク

`task.md` の構造に沿って書く。

```markdown
### 概要

何を、なぜ行うのか。

### 背景・現状

現在の構成、課題、関連コード、背景。

### 対象範囲

今回実施する作業範囲。

### 対象外

今回実施しないもの。

### 作業項目

- [ ] 実施する作業

### 受け入れ条件

- [ ] 客観的に確認可能な条件

### 検証方法

- 実行するテスト、型チェック、ビルド、手動確認

### 実装上の補足

調査で判明した関連ファイル、設定、テスト、CI、注意事項。
```

## GitHub MCP

- `git remote -v` からリポジトリの完全名を判断する。リモートが異なる情報を示さない限り、このリポジトリは `yamaoyu/dog-health` と想定する。
- 利用可能な場合は、GitHub MCP/GitHubコネクタのIssue作成ツールを使う。
- GitHub MCPが利用できない場合は、このワークフローではCodexからIssue作成を完了できないことを報告する。
