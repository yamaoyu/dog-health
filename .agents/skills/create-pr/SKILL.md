# PR 作成

このSkillは、実装完了後にユーザーがPR作成を求めた場合に使う。

## 手順

1. `git status --short --branch` を実行し、現在のブランチを確認する。
2. PRに適したブランチであることを確認する。デフォルトブランチ上にいる場合は、続行前に止まってユーザーに確認する。
3. `git diff` で差分全体を確認する。必要に応じてステージ済み差分やコミット差分も確認する。
4. ブランチ名、コミットメッセージ、ユーザー要求、既存の文脈から関連Issueを特定する。
5. Issue番号が存在し、ツールが利用可能な場合は、GitHub MCP/GitHubコネクタを使って関連Issueを確認する。必要なGitHub MCPアクセスが利用できない場合は、代替手段を使わずユーザーに伝える。
6. 実装内容とIssueの受け入れ条件を比較し、満たしていない条件があれば明示する。
7. 関係のない変更が含まれていないか確認する。関係のないユーザー変更をコミットやPRに含めない。
8. `AGENTS.md` と、`.github/pull_request_template.md`、`.github/workflows/`、`frontend/package.json`、`backend/requirements.txt`、影響を受けるテストなどの関連ファイルを読む。
9. 関連する検証コマンドを実行し、正確な結果を記録する。実際に実行して成功した確認だけを成功と書く。
10. 検証が失敗した場合は、PR作成前に原因を調査する。失敗が無関係な場合やスコープ内で安全に修正できない場合は、ユーザーに伝える。
11. 最終差分をもう一度確認する。
12. コミットが必要な場合は、関連する変更だけを含む意図の明確なコミットを作成する。
13. ブランチをプッシュする。
14. GitHub MCP/GitHubコネクタを使ってドラフトPRを作成する。コネクタまたはPR作成ツールが利用できない場合はユーザーに伝え、`gh` や生のAPI呼び出しなどの代替手段を勝手に使わない。

## 検証

コマンドを選ぶ前にリポジトリを確認する。現在想定される確認は次の通り。

- フロントエンド変更: `frontend/` で `npm run type-check` と `npm test` を実行する。ビルド出力やバンドル挙動が関係する場合は `npm run build` も実行する。
- バックエンド変更: `backend/` で `python -m pytest` を実行する。
- PR全体の検証: `.github/workflows/test.yml` に合わせる。現在はフロントエンドの型チェック/テストとバックエンドのpytest。

依存関係が不足していてインストールが必要な場合は、ネットワークを使うインストールコマンドの前に承認を求める。

## PR本文形式

`.github/pull_request_template.md` が存在する場合は優先する。テンプレートがない場合は、次のMarkdown構造を使う。

```markdown
## 概要

変更内容とその理由。

## 変更内容

- 主要な変更点

## 検証結果

- 実行したコマンド: 結果

## 関連Issue

Closes #<issue-number>

## リスク・補足事項

既知のリスク、トレードオフ、未解決事項。
```

このリポジトリの現在のテンプレートを使う場合は、次の既存見出しに日本語の本文を対応させる。

```markdown
## Purpose

## Changes

- 

## Issues

Closes #<issue-number>
```

## ルール

- 原則としてドラフトPRを作成する。
- タイトルは簡潔にし、変更される振る舞いが分かる内容にする。
- 関連Issueが存在する場合は必ずリンクする。
- 失敗したテストや未実行の検証を隠さない。
- 関係のない変更を含めない。
- ユーザーが明示的に求めない限り、ユーザー変更を上書きしたりrevertしたりしない。
- PR作成には GitHub MCP/GitHubコネクタを使う。利用できない場合は停止し、制限を報告する。
